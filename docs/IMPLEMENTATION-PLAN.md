조직에 스킬이 몇 개 흩어져 있는지 모르면 나머지는 전부 추측이다.

| 작업 | 산출물 | 검증 |
|---|---|---|
| 자가진단 스크립트 작성 | `scripts/inventory.sh` | 로컬에서 실행해 이름·설명·해시 목록이 나옴 |

**설계 원칙**: 스크립트는 **읽기 전용**이고 결과 제출은 **본인 손**에 있다. 개인 홈 디렉터리를 중앙에서 스캔하지 않는다 — 이 프로젝트는 신뢰 위에서만 굴러간다.

**리스크**: 응답률 미달. → 파일럿 팀만으로 Phase 1 진행하고, 나머지는 Phase 3 배포 시점에 자연 수집.

## Phase 1 — 골격 (9/18~10/1, 2주)

**개인 저장소에서 먼저 만들고, 조직으로 옮긴 뒤 실측한다.**

### 1주차 — 개인 GitHub에서 구조 검증

| 작업 | 검증 |
|---|---|
| `catalog-skeleton/`을 개인 저장소로 push | — |
| `/plugin marketplace add <개인계정>/<repo>` | 마켓플레이스가 인식됨 |
| 4개 플러그인(common/platform/sales/finance) 설치 | 스킬 목록에 나타남 |
| 예제 스킬 자동 발동 테스트 | 자연어로 불렀을 때 스킬이 뜸 |
| `marketplace.json` / `plugin.json` 스키마 확정 | 오류 없이 로드 |

> ⚠️ **SEC-5**: 개인 저장소에는 **더미 데이터만.** 사내 팀명·업무 절차·견적 관련 내용 금지.

**여기서 검증되지 않는 것**: 배포 등급, 서버 관리 설정, 조직 자동 갱신. 전부 관리자 콘솔이 필요하다.

### 2주차 — 조직 이전 + 실측

| 작업 | 검증 |
|---|---|
| GitHub 저장소 **transfer**로 조직 계정 이전 (히스토리 유지) | 커밋 이력 보존 |
| CODEOWNERS · 브랜치 보호 규칙 설정 | 오너 승인 없이 머지 불가 |
| 관리자 콘솔에 조직 마켓플레이스 등록 | 파일럿 팀에 노출됨 |
| 파일럿 팀 1개 설치 | 설치 성공 |

**§11 미해결 5건 실측 — Phase 1의 진짜 목적**

| # | 실측 항목 | 방법 |
|---|---|---|
| 1 | 조직 마켓플레이스 **등록 경로** (콘솔 vs 설정파일) | 콘솔에서 등록 시도 |
| 2 | **자동 갱신 기본값** — 관리자가 v1.1을 올리면 도달하는가 | 버전 올리고 파일럿 PC에서 확인 |
| 3 | **동기화 트리거** — version bump인가 임의 커밋인가 | 버전 안 올리고 커밋만 해봄 |
| 4 | **커밋 SHA 핀 문법** | `#<sha>` 형태 시도 |
| 5 | **컨텍스트 1% 상한** — 스킬 몇 개부터 description이 잘리는가 | 더미 스킬을 늘려가며 관찰 |
| 6 | **에이전트에 배포 등급이 적용되는가** | `agents/` 포함 플러그인을 Required로 지정 |

**완료 기준**: 파일럿 팀 설치 성공 **+ 관리자가 올린 갱신이 실제로 도달함을 확인** + 위 6건 결과 문서화.

**이 Phase가 가장 위험하다.** 2번이 "기본 off"로 나오면 §10 최상위 리스크가 현실이 된다. 그 경우 대응책(사용자 안내 vs 설정 강제)을 즉시 결정해야 한다.

## Phase 2 — 게이트 (10/2~10/10, 1.5주)

| 작업 | 산출물 | 검증 |
|---|---|---|
| 구조 린트 | `scripts/lint_structure.py` | 필수 frontmatter 누락·description 초과를 잡아냄 |
| 위험도 자동 판정 | 같은 스크립트 | `scripts/` 있는 플러그인이 `needs-review`로 분류됨 |
| 보안 스캔 | `scripts/scan_security.py` | 네트워크 호출·셸 실행·인젝션 패턴 탐지 |
| CI 워크플로 | `.github/workflows/skill-ci.yml` | PR에서 2종이 하드 게이트로 동작 |
| PR 템플릿 | `.github/PULL_REQUEST_TEMPLATE.md` | 필수 항목 미기입 시 린트가 잡음 |
| eval 실행(경고) | CI 잡 1개 | 결과가 PR 코멘트로 게시되되 **머지를 막지 않음** |
| `/skill-submit` 커맨드 | `common` 플러그인에 포함 | 로컬 스킬 → PR 생성이 한 번에 |

**완료 기준**: 파일럿 팀원 1명이 실제로 스킬을 제출해 **게이트를 거쳐 머지**됨. 문서형 스킬은 사람 승인 없이, 스크립트 포함 스킬은 승인을 거쳐서.

**축소 근거**: eval을 하드 게이트에서 뺐다. LLM 호출은 비결정론적이라 같은 PR이 두 번 다른 결과를 낼 수 있고, 랜덤하게 실패하는 게이트는 곧 우회된다. 케이스는 계속 쌓아 Phase 5의 자산으로 쓴다.

**선행 조건 2건이 이 Phase 이전에 끝나야 한다.**
- §11-4 `OTEL_LOG_TOOL_DETAILS=1` **조직 동의** — 승인 주체 지정 + 사전 공지
- §11-6 **OTel Collector 호스팅 위치** 확정

| 작업 | 산출물 | 검증 |
|---|---|---|
| OTel Collector 최소 구성 | 사내 서버 1대, OTLP 수신 → 파일 적재 | 메트릭이 실제로 들어옴 |
| 텔레메트리 env 배포 (서버 관리 설정) | `CLAUDE_CODE_ENABLE_TELEMETRY`, `OTEL_LOG_TOOL_DETAILS=1` 등 | 스킬 이름이 `custom`이 아니라 실명으로 찍힘 |
| 주간 집계 스크립트 | `scripts/aggregate.py` | 스킬별 호출·비용 표 산출 |
| 정적 HTML 대시보드 | `dashboard.html` (주 1회 생성) | 3개 뷰가 렌더됨 |
| 관리자 대시보드 CSV 월 1회 내보내기 | 절차 문서 | 전체 채택률 확인 |

**대시보드 3개 뷰**
1. 호출 상위 스킬
2. **30일 0회 스킬** (폐기 후보) ← Phase 5의 입력
3. 플러그인(팀)별 사용량 + 스킬별 토큰 비용

**측정 불가 확정**: 누가 어떤 플러그인을 **설치**했는지, Required의 **도달률**. → "쓰였는가"를 대리 지표로 사용.

**축소 근거**: Grafana 스택 대신 정적 HTML. 50명 조직의 스킬 사용량은 주 단위로 보면 충분하고, Phase 5가 필요로 하는 건 화면이 아니라 "이번 달 하위 스킬 목록"이라는 데이터다. 나중에 Grafana로 올리는 건 언제든 가능하다.

## Phase 5 — 개선 루프 (10/22~11/4, 2주)

**이 프로젝트의 차별점.** 조사한 어떤 제품도 사용량을 평가 파이프라인에 자동 연결하지 않았다.

| 작업 | 산출물 | 검증 |
|---|---|---|
| 월간 eval 배치 | GitHub Actions 스케줄 잡 | 상위 스킬의 eval이 재실행됨 |
| 점수 하락 감지 → 이슈 생성 | 배치 스크립트 | 하락 시 오너에게 이슈가 자동 열림 |
| 분기 폐기 리뷰 | 배치 + 절차 문서 | 90일 0회 스킬 목록 → 오너 통보 |
| deprecated 처리 절차 | `docs/CONTRIBUTING.md` | 2주 무응답 시 처리 경로가 명시됨 |
| 모델 릴리스 대응 절차 | 문서 | 신규 모델 출시 = eval 전체 재실행 트리거 |

**완료 기준**: **첫 폐기 결정 1건 실행.** 데이터로 후보를 뽑고, 오너가 판단하고, 실제로 내린다.

**원칙(FR-704)**: 자동 개선은 하지 않는다. 배치는 **후보를 제시**하고, 판단과 수정은 사람이 한다.
