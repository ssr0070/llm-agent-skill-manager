# 스킬·플러그인 제출

완성한 스킬을 접수 저장소 `example-org/ai-skill-inbox`의 `skills/<팀>/<이름>/`에, 플러그인을 `plugins/<팀>/<이름>/`에 올리는 PR을 만든다. 팀장(`lead-<팀>` 팀의 구성원)에게는 재검사를 통과한 뒤 `intake`가 리뷰를 요청한다. 접수는 3단계다. **제출 전 점검**(작성자가 이 스킬로 정적 검사를 직접 돌려 통과 보고서를 만든다) → **제출 후 재검사**(팀장 승인 전에 배포 저장소의 `intake`가 매시 정각, 보고서가 제출 내용과 같은지 확인하고 같은 검사를 다시 해 결과를 PR 코멘트로 단다) → **사람 검토**(팀장의 업무 검토. L2만 승인자의 보안 검토를 더 거친다). 통과 보고서가 없으면 PR을 만들지 않는다. 재검사 결과는 접수 PR의 코멘트로, 배포 결과는 배포 저장소의 PR(검토 대기)이나 접수 저장소의 이슈(반려)로 알려 주고, 담당자(스킬은 `metadata.owner`, 플러그인은 `plugin.json`의 `author.email`)에게 메일로도 간다.

제출 단위는 폴더를 보고 정한다. `.claude-plugin/plugin.json`이 있으면 플러그인, `SKILL.md` 하나뿐이면 스킬이다. 스킬 여럿이나 에이전트·hook·공용 scripts를 가진 것은 플러그인으로만 낼 수 있다. 사용자가 스킬로 내려는 폴더에 `SKILL.md`가 둘 이상이면 플러그인으로 내자고 안내한다.

## 1. 제출 전 점검

사용자가 "제출 전 점검", "내 스킬 검사해줘"처럼 점검만 요청하면 이 절(1-1, 1-2)까지만 하고 멈춘다. 제출은 사용자가 요청할 때 2절부터 한다.

### 1-1. 점검 에이전트

제출할 폴더를 사용자에게 확인받은 뒤, `common-toolkit:common-skill-reviewer` 에이전트에게 그 폴더 경로를 넘겨 점검을 맡긴다. 작성 대화의 맥락 없이 파일만 보고 판단해야 하므로, 이 대화에서 직접 점검하지 않는다. 플러그인이면 `skills/` 아래 스킬 폴더마다 에이전트를 부르되, 팀 접두어와 `metadata.owner`·`metadata.team`은 플러그인에서 요구하지 않는다고 함께 알린다(이름 공간이 `<플러그인>:<스킬>`이고 담당자는 `plugin.json`에 있다).

플러그인은 에이전트 점검과 별도로 다음을 이 대화에서 직접 확인한다. 자동 정적 검사가 같은 조건으로 반려하기 때문이다.

- `plugin.json`의 `name`이 폴더 이름과 같고, `author.email`이 사내 주소(`example.com`, `example.io`)다.
- 이미 배포된 플러그인이면 `version`이 배포본보다 높다. 배포본은 `gh api repos/example-org/ai-marketplace/contents/plugins/<team>/<name>/.claude-plugin/plugin.json -q .content | base64 -d`로 본다(404면 신규).
- `dependencies`의 플러그인이 모두 배포 카탈로그(`gh api repos/example-org/ai-marketplace/contents/.claude-plugin/marketplace.json -q .content | base64 -d`)에 있다. 없으면 그 플러그인을 먼저 제출해야 한다고 안내하고 멈춘다.
- `evals/<케이스>/prompt.md`가 3건 이상 있다. `evals/results/`, `__pycache__`, 심볼릭 링크는 뺀다.
- 플러그인은 hook·scripts·에이전트 때문에 거의 언제나 L2이므로, 승인자가 원문을 읽고 병합 전 eval을 돌려 검토가 길어진다고 안내한다.

- 에이전트의 보고서를 사용자에게 그대로 보여 준다.
- "차단"이 하나라도 있으면 올리지 않는다. 사용자가 고친 뒤 다시 제출을 요청하면 처음부터 다시 점검한다.
- `benchmark.json`이 없다는 차단은 skill-creator 평가를 먼저 실행하자고 안내한다.
- 에이전트가 plugin eval 케이스를 새로 만들었으면, 사용자가 케이스를 열어 통과 기준을 확인했는지 물은 뒤 다음 단계로 간다.
- 예상 등급이 L2면 승인자가 원문을 읽고 병합 전 평가를 돌리므로 검토가 길어질 수 있다고 안내한다. L3이면 조직 번들로 배포되지 않으므로 올리지 않는다.
- 에이전트를 부를 수 없으면 `common-skill-guide`의 규칙으로 직접 점검하고, 맥락 없는 점검이 아니었다는 점을 사용자에게 알린다.
- 폴더 안에 심볼릭 링크가 있으면 실제 파일로 바꾸자고 안내한다. 자동 검사가 받지 않는다.

### 1-2. 정적 검사 직접 실행

배포 저장소의 자동 정적 검사와 같은 기준으로 만든 `scripts/precheck.py`를 돌린다. 이 SKILL.md가 있는 스킬 폴더의 `scripts/precheck.py`다. 아래 명령의 `<스킬 폴더>`는 그 폴더의 절대 경로로 바꾼다.

```
uv run --script "<스킬 폴더>/scripts/precheck.py" <제출할 폴더> [--team <팀>]
```

- 플러그인은 `plugin.json`에 팀이 없으므로 리뷰할 팀장의 팀을 `--team`으로 넘긴다. 스킬은 `metadata.team`을 쓴다.
- `uv`가 없으면 `python`으로 실행해도 되지만 PyYAML이 있어야 한다. 설치 안내는 `https://docs.astral.sh/uv/`다.
- `skillspector`나 `skill-scanner`가 없다는 ❌가 나오면 아래 명령으로 설치하게 안내하고, 설치한 뒤 다시 돌린다. 검사 도구가 없으면 통과로 보지 않는다. 배포 저장소의 재검사와 같은 버전이어야 결과가 같으므로 아래 버전을 그대로 쓴다.
  ```
  uv tool install git+https://github.com/NVIDIA/skillspector.git@11c8b48e35056602fad263438448e0ffb5be2776
  uv tool install cisco-ai-skill-scanner==2.2.1
  ```
- 보고서를 사용자에게 그대로 보여 준다. ❌가 하나라도 있으면 제출하지 않는다. 고칠 방법을 함께 안내하고, 사용자가 고친 뒤 처음부터(1-1) 다시 점검한다.
- 예외: 남은 ❌가 SkillSpector HIGH뿐이라는 안내(ℹ️)가 나오면, 보고서 끝의 'SkillSpector HIGH 이상 검출' 표를 사용자와 함께 본다.
  - 검출마다 그 파일과 줄을 열어, 규칙이 막으려는 동작(숨은 지시, 문자 제거·디코딩 지시, 셸 실행, 프롬프트 유출 등)을 실제로 하는지 확인한다.
  - 실제 위험이거나 고칠 수 있으면 고친다. 스캐너를 피하려고 뜻이 같은 다른 문구로 바꾸지는 않는다. 그런 수정은 진짜 악성 지시를 숨기는 방법과 구별되지 않기 때문이다.
  - 사용자가 오탐이라고 판단하면 같은 명령에 `--request-exception`을 붙여 다시 돌린다. 종료 코드 3과 함께 보고서 결과가 '⏸ 승인자 예외 요청'이 되면 제출할 수 있다. 승인자가 배포 저장소에서 검출마다 원문을 읽고 판정한다.
  - CRITICAL, 검사 시간 한도로 생긴 미완료, 다른 ❌가 있으면 예외를 요청할 수 없다. 시간 한도 문제는 스킬의 크기(예시·참고 파일)를 줄여 해결한다.
- ⚠️는 반려 사유가 아니지만 승인자 보고서에 그대로 올라간다고 알린다.
- 보고서를 손으로 고치지 않는다. 보고서의 내용 해시가 제출 내용과 다르면 재검사에서 반려된다.

## 2. 접수 저장소에 PR 만들기

`git`과 `gh`가 있고, `gh`가 사용자 본인의 GitHub 계정으로 로그인되어 있어야 한다(`gh auth status`). 접수 저장소에 쓰기 권한이 없으면 승인자에게 초대를 요청하라고 안내하고 멈춘다.

`<kind>`는 스킬이면 `skills`, 플러그인이면 `plugins`다. `<team>`은 스킬이면 `metadata.team`이고, 플러그인이면 리뷰할 팀장이 속한 팀을 사용자에게 묻는다(`plugin.json`에는 팀이 없다). `<name>`은 스킬의 `name` 또는 `plugin.json`의 `name`, `<시각>`은 `yyyyMMddHHmm`이다. 작업 폴더는 사용자 프로젝트가 아닌 임시 폴더에 둔다.

1. 접수 저장소를 임시 폴더에 받는다: `gh repo clone example-org/ai-skill-inbox <임시 폴더> -- --depth 1`
2. 새 브랜치를 만든다: `git -C <임시 폴더> switch -c submit/<name>-<시각>`
3. `<임시 폴더>/<kind>/<team>/<name>/`을 지우고, 폴더의 내용을 그 자리에 복사한다. 수정 제출이면 기존 폴더가 교체된다.
4. **복사한 폴더로 정적 검사를 다시 돌린다.** 1-2를 통과한 뒤에도 실제로 올라갈 내용으로 보고서를 만들어야 하기 때문이다. 보고서는 임시 폴더 밖에 쓴다.
   ```
   uv run --script "<스킬 폴더>/scripts/precheck.py" <임시 폴더>/<kind>/<team>/<name> [--team <팀>] --out <보고서 파일>
   ```
   종료 코드가 0이 아니면(❌가 있으면) 여기서 멈추고, 보고서를 보여 주며 1절로 돌아간다. 1-2에서 예외를 요청했다면 같은 `--request-exception`을 붙이고, 종료 코드 3(예외 요청)이면 계속한다.
5. 그 폴더만 커밋한다: `git -C <임시 폴더> add <kind>/<team>/<name>` 후 `git -C <임시 폴더> commit -m "submit: <name>"`
6. 커밋된 내용이 보고서와 같은지 확인한다: `git -C <임시 폴더> rev-parse HEAD:<kind>/<team>/<name>`의 값이 보고서 마지막 줄(precheck 표지)의 `tree=` 값과 같아야 한다. 다르면 전역 `.gitignore` 등으로 일부 파일이 빠진 것이므로, 빠진 파일을 사용자에게 알리고 멈춘다.
7. 올린다: `git -C <임시 폴더> push -u origin submit/<name>-<시각>`
8. PR을 만든다. 본문은 저장소의 PR 양식 항목을 채우고, 점검 에이전트의 예상 등급을 한 줄 덧붙인다. 예외를 요청했다면 `## 예외 요청 사유` 절을 두고, 보고서의 HIGH 표의 검출마다 오탐이라고 본 이유를 한 줄씩 적는다(사용자가 원문을 읽고 판단한 내용). 그 뒤 **4번의 보고서 파일 내용을 끝에 그대로 붙인다.** 보고서의 마지막 줄(precheck 표지)이 빠지면 재검사에서 떨어진다. 본문은 파일로 만들어 넘긴다. 리뷰어는 지정하지 않는다. 재검사를 통과하면 `intake`가 팀장에게 리뷰를 요청하므로, 팀장은 검사를 통과한 PR만 받는다.
   ```
   gh pr create -R example-org/ai-skill-inbox --base main --head submit/<name>-<시각> \
     --title "[<team>] <name>" --body-file <본문 파일>
   ```
9. 임시 폴더와 보고서 파일을 지운다.

## 3. 제출 후 안내

사용자에게 PR 링크와 함께 다음을 알려 준다.

- 제출 전 점검 보고서가 PR 본문에 붙었다. 다음 정각에 제출 후 재검사가 돌고, 결과가 PR 코멘트로 달린다.
- 예외를 요청했다면 재검사가 '⏸ 승인자 예외 판정 대기' 코멘트를 달고 승인자에게 메일을 보낸다. 승인자가 오탐으로 판정해 예외를 등록하면 다음 정각에 다시 검사해 통과시키고, 아니면 PR에 수정 요청을 남긴다. 판정을 기다리는 동안 커밋을 더하면 지문이 바뀌어 다시 판정받아야 한다. 예외가 적용된 제출은 L2로 배포된다.
- 재검사를 통과하면 팀장에게 GitHub 리뷰 요청 알림이 간다. 팀장이 승인하면 다음 정각에 자동으로 병합되고 배포 저장소에 배포 PR이 생긴다. 팀장이 병합 버튼을 누를 필요는 없다.
- 예상 등급이 L1이면 배포 PR이 바로 병합되어 팀장 승인만으로 배포된다. L2이면 승인자의 보안 검토를 거친다. 사내 데이터에 접근하거나 고객에게 나가는 문서를 만드는 스킬이면 접수 PR에 `L2` 라벨을 달자고 안내한다.
- 배포되면 담당자와 관리자에게 배포 완료 메일이 가고, 30분 안에 직원 화면에 반영된다.
- 재검사에서 떨어지면 담당자에게 메일이 간다. 이때는 새 PR을 만들지 않고 **같은 PR을 고친다**(4절). 팀장 승인 전이므로 다시 승인받을 일이 없다.
- 팀장 승인 뒤에 커밋을 더하면 승인이 무효가 되고, 재검사도 다시 돈다. 고친 뒤에는 다시 승인을 받는다.
- 팀장이 PR을 닫았거나 승인자가 보안 검토에서 반려하면, 같은 폴더를 고치는 새 PR로 다시 제출한다. 이때도 제출 전 점검부터 다시 한다. 플러그인은 다시 낼 때마다 `plugin.json`의 `version`을 올린다.
- 플러그인이 배포되면 `<플러그인 이름>:<스킬 이름>`으로 불린다. 원본 저장소를 따로 두고 개발한다면, 고친 뒤 접수 저장소에 다시 제출해야 조직에 반영된다.
- 같은 스킬을 개인 스킬로 업로드하거나 공유하지 않는다. 배포 후 조직 번들과 중복된다.
- 배포 후 모델이 바뀌면 회귀 평가가 돈다. 기준에 못 미치면 수정 요청 메일이 온다.

## 4. 재검사에서 떨어졌을 때: 같은 PR 고치기

PR 코멘트의 ❌ 항목을 사용자와 함께 고친 뒤, 새 PR이 아니라 같은 PR의 브랜치에 커밋을 더한다.

1. 고친 폴더로 1절(제출 전 점검)을 다시 한다. ❌가 있으면 멈춘다.
2. PR의 브랜치를 임시 폴더에 받는다: `gh repo clone example-org/ai-skill-inbox <임시 폴더> -- --depth 1 --branch <PR 브랜치>`. 브랜치 이름은 `gh pr view <번호> -R example-org/ai-skill-inbox --json headRefName -q .headRefName`로 본다.
3. 2절의 3~6번처럼 폴더를 교체하고, 복사한 폴더로 정적 검사를 돌려 새 보고서를 만들고, 커밋한 뒤 해시를 확인한다. 커밋 메시지는 `fix: <name>`으로 한다.
4. 올린다: `git -C <임시 폴더> push`
5. PR 본문의 보고서를 새 보고서로 바꾼다. 본문에서 `## 제출 전 점검 보고서`부터 끝까지를 새 보고서로 바꾼 파일을 만들어 `gh pr edit <번호> -R example-org/ai-skill-inbox --body-file <본문 파일>`로 넘긴다. 바꾸지 않으면 해시가 맞지 않아 다시 떨어진다.
6. 다음 정각에 재검사가 다시 돈다고 알리고, 임시 폴더와 보고서 파일을 지운다.
