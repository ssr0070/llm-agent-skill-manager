# 스킬 접수함

> 사내 스킬 접수 저장소(ai-skill-inbox)의 접수 체계만 옮긴 공개본입니다. 직원이 제출한 스킬·플러그인은 뺐고, 조직명·메일 도메인은 예시값(`example-org`, `example.com`)으로 바꿨습니다. 검사와 병합을 맡는 배포 저장소(`ai-marketplace`)의 워크플로는 포함하지 않습니다.

직원이 만든 스킬과 플러그인을 받아 검사·검토한 뒤 전 직원에게 배포하는 저장소입니다. 작성 규칙은 `common-skill-guide` 스킬에 있습니다.

## 제출하기

Claude Code에서 이렇게 말하면 됩니다.

> 스킬 제출해줘 (플러그인이면 "플러그인 제출해줘")

`common-submit-skill`이 먼저 점검하고, 통과하면 점검 보고서를 붙여 PR까지 만듭니다. 점검만 해 보려면 "제출 전 점검해줘"라고 합니다. **리뷰어는 지정하지 않습니다.** 재검사를 통과하면 팀장에게 리뷰 요청이 자동으로 갑니다.

제출 전에 준비할 것은 둘입니다.

- skill-creator로 만든 폴더와 평가 파일: `evals/evals.json`(질문 3건 이상), `evals/benchmark.json`, plugin eval 케이스 3건 이상
- 검사 도구: 처음 한 번만 설치합니다. 아래 [검사 도구 설치](#검사-도구-설치)를 봅니다.

스킬로 낼지 플러그인으로 낼지는 다음 표로 정합니다.

| | 스킬 | 플러그인 |
|---|---|---|
| 이럴 때 | 스킬 하나 | 에이전트나 hook이 있거나, 스킬 여럿이 scripts·규칙 문서를 함께 씀 |
| 올리는 곳 | `skills/<팀>/<스킬 이름>/` | `plugins/<팀>/<플러그인 이름>/` |
| 폴더 이름 | `SKILL.md`의 `name`과 같게 | `plugin.json`의 `name`과 같게 |

`<팀>`은 `common` `mkt` `sales` `rnd` `dev` `content` `hr` `fin` 중 하나입니다.

## 제출한 뒤에 일어나는 일

| 단계 | 누가 | 하는 일 |
|---|---|---|
| 1. 재검사 | 자동, 매시 정각 | 같은 기준으로 다시 검사하고 결과를 PR 코멘트로 남깁니다. 통과하면 팀장에게 리뷰 요청이 갑니다. |
| 2. 업무 검토 | 팀장 | 업무에 맞는지 보고 승인합니다. 다음 정각에 자동으로 병합됩니다. |
| 3. 보안 검토 | 승인자 | **L2만** 거칩니다. hook·MCP·scripts·쓰기 권한이 있거나 `L2` 라벨이 붙은 것이 L2입니다. 나머지(L1)는 이 단계 없이 배포됩니다. |
| 4. 배포 | 자동 | 30분 안에 전 직원에게 반영되고, 작성자에게 배포 완료 메일이 갑니다. |

자동 검사를 팀장 검토보다 먼저 하므로, 검사에서 떨어져도 팀장 승인을 다시 받을 일이 없습니다.

## 떨어지거나 보류되면

| 이런 일이 생기면 | 이렇게 합니다 |
|---|---|
| 제출 전 점검에서 ❌가 나옴 | PR이 만들어지지 않습니다. 보고서의 ❌ 항목을 고치고 다시 점검합니다. |
| 재검사를 통과하지 못함 (PR 코멘트와 메일로 알림) | **같은 PR**을 고칩니다. Claude Code에서 "재검사 떨어진 거 고쳐서 다시 올려줘"라고 하면 됩니다. 다음 정각에 다시 검사합니다. |
| 팀장이 변경을 요청함 | 같은 PR을 고칩니다. 재검사를 통과하면 리뷰 요청이 다시 갑니다. |
| 승인 뒤에 커밋을 더함, 자동 병합이 충돌로 실패함 | 승인이 무효가 됩니다. 고친 뒤 재검사를 거쳐 다시 승인받습니다. |
| `[반려]` 이슈나 반려 메일을 받음 | 사유를 고쳐 **새 PR**로 냅니다. 병합 뒤 검사에서 떨어졌거나 승인자가 보안 검토에서 반려한 경우입니다. |
| 팀장이 PR을 닫음 | 배포되지 않습니다. 필요하면 팀장과 협의한 뒤 새 PR로 냅니다. |

## 지켜야 할 것

- PR 하나에는 폴더 **하나만** 바꿉니다. 폴더 밖의 파일을 바꾸면 반려됩니다.
- 이미 배포된 스킬을 고칠 때는 같은 폴더를 고치는 새 PR로 냅니다.
- 다른 사람의 폴더는 고치지 않습니다. 고칠 점은 담당자(`metadata.owner` 또는 `author.email`)에게 알립니다.
- 심볼릭 링크, `__pycache__`, `evals/results/`는 넣지 않습니다.
- 자기 PR을 스스로 승인하거나 `main`에 직접 올린 변경은 배포되지 않습니다.

## 팀장에게

- 리뷰 요청은 재검사를 통과한 PR에만 갑니다. 검사 항목은 다시 보지 않아도 됩니다.
- 업무 내용만 봅니다. 우리 팀 업무에 맞는지, 산출물 양식과 용어가 맞는지, 같은 일을 하는 스킬이 이미 있는지 확인합니다.
- 승인(Approve)만 누르면 병합은 자동으로 됩니다. 보류하려면 승인하지 않고 코멘트나 변경 요청을 남깁니다.
- **L1은 팀장 승인만으로 배포됩니다.** 고객 정보·인사·원가 같은 사내 데이터를 다루거나 고객에게 나가는 문서를 만드는 스킬이면, 승인하기 전에 PR에 `L2` 라벨을 달아 승인자에게 보냅니다. 한 번 단 라벨은 나중에 떼어도 L2로 봅니다.
- 팀장 본인이 만든 스킬은 다른 팀장이나 승인자에게 승인받습니다.

## 더 알아보기

### 검사 도구 설치

정적 검사에는 `uv`, `skillspector`, `skill-scanner`가 필요합니다. 처음 한 번 아래 두 명령으로 설치합니다. 버전이 재검사와 같아야 결과가 같고, 도구가 없으면 통과로 보지 않습니다.

```bash
uv tool install git+https://github.com/NVIDIA/skillspector.git@11c8b48e35056602fad263438448e0ffb5be2776
uv tool install cisco-ai-skill-scanner==2.2.1
```

<details>
<summary>웹 화면으로 제출하기</summary>

웹 화면으로 올려도 점검 보고서는 있어야 합니다. 먼저 Claude Code에서 "제출 전 점검해줘"로 보고서를 받아 둡니다.

1. 이 저장소의 `skills/<팀>/`(플러그인은 `plugins/<팀>/`) 폴더에서 **Add file > Upload files**를 누릅니다.
2. 폴더를 통째로 끌어다 놓습니다.
3. **Create a new branch for this commit and start a pull request**를 고르고 PR을 만듭니다. PR 본문 끝에 보고서 전체를 붙여 넣습니다. 마지막 줄 `<!-- precheck: ... -->`가 빠지면 반려됩니다.
4. 리뷰어는 지정하지 않습니다.

</details>

<details>
<summary>플러그인을 낼 때 더 볼 것</summary>

- `plugin.json`의 `author.email`은 사내 주소여야 합니다. 반려·배포 메일이 이 주소로 갑니다.
- 다시 낼 때는 `plugin.json`의 `version`을 배포된 것보다 올립니다. 스킬과 달리 자동으로 올라가지 않습니다.
- `dependencies`에 적은 플러그인이 모두 배포되어 있어야 합니다. 없으면 그 플러그인을 먼저 냅니다.
- plugin eval 케이스는 `evals/<케이스>/`에 3건 이상 둡니다(`claude plugin eval` 표준 배치).
- 스킬 이름에 팀 접두어는 붙이지 않아도 됩니다. `<플러그인>:<스킬>`로 불립니다.
- 플러그인은 대부분 L2라서 승인자가 에이전트·hook 원문을 직접 읽고 eval을 돌립니다. 스킬보다 검토가 오래 걸립니다.

</details>

<details>
<summary>검사 항목 전체</summary>

제출 전 점검과 재검사는 같은 기준으로 파일만 읽어 검사하고, 스킬 코드는 실행하지 않습니다. 병합 뒤 배포 PR을 만들 때 한 번 더 검사합니다. 승인, MCP 차단 목록, 배포본 버전, 의존 플러그인은 재검사에서만 확인하므로 제출 전 점검을 통과해도 재검사에서 걸릴 수 있습니다. 걸린 항목은 한 번에 모아 알려 줍니다.

| 구분 | 확인 내용 |
|---|---|
| 점검 보고서 | PR 본문에 **통과** 보고서가 있고, 보고서의 내용 해시가 PR 마지막 커밋의 폴더와 같음. 이것만 걸렸다면 본문의 보고서만 새로 바꿔도 됨 |
| 접수 범위 | 허용된 팀의 폴더 하나만 바꿈 |
| 승인 | `lead-<팀>` 또는 `skill-approvers` 구성원이 재검사를 통과한 마지막 커밋을 승인함. 본인 승인은 인정하지 않음 |
| 파일 | PR 마지막 커밋의 파일만 씀. 심볼릭 링크 거부 |
| 메타데이터 | 스킬: `SKILL.md`가 하나, `name`이 폴더 이름과 같음, `metadata.team`이 폴더의 팀과 같음, `metadata.owner`가 사내 메일<br/>플러그인: `author.email`이 사내 주소, 다른 플러그인과 이름이 겹치지 않음, `dependencies`가 모두 배포되어 있음 |
| 규격 | `claude plugin validate` 통과, 최상위 `bin/` 없음, 버전이 배포본보다 높음(스킬은 자동으로 올림) |
| 이름과 설명 | 이름은 소문자·숫자·하이픈 64자 이내(팀 번들 스킬은 `<팀>-` 접두어), `description`은 1~1,024자 |
| 평가 파일 | `evals/evals.json` 질문 3건 이상, `evals/benchmark.json`, plugin eval 케이스 3건 이상 |
| 권한 | `allowed-tools`에 `*`, `Bash`, `도구(*)`처럼 실행 권한을 통째로 여는 항목이 없음 |
| 보안 스캔 | SkillSpector 위험 점수 50 이하, HIGH 이상 검출 없음, 분석 중단 없음 / Cisco skill-scanner HIGH 이상 검출 없음 |
| MCP 출처 | MCP 서버의 발행자나 국가가 차단 목록에 없음 |

경고만 하는 항목도 있습니다. `description` 150~300자 권장, 번들 Always-on 토큰 2,000 초과, SkillSpector MEDIUM 검출, 이름·설명이 60% 이상 비슷한 기존 스킬은 승인자 보고서에 표시만 합니다.

</details>

<details>
<summary>관리자용</summary>

- 이 저장소에는 워크플로와 비밀 값을 두지 않습니다. 저장소 설정에서 Actions를 꺼 둡니다. 검사와 병합은 배포 저장소(`ai-marketplace`)의 `intake` 워크플로가 합니다.
- 팀장 팀(`lead-<팀>`)과 승인자 팀(`skill-approvers`)의 구성원은 조직 Owner만 바꿉니다.
- 이 저장소에 `L2` 라벨을 만들어 둡니다.
- 배포된 스킬에 문제가 있으면 승인자가 배포 저장소의 Actions > `recall`을 실행해 회수합니다. 30분 안에 직원 화면에서 사라집니다. 병합을 되돌리면(revert) 버전이 낮아져 직원 PC에서 사라지지 않을 수 있으므로 쓰지 않습니다.
- `scripts/` 밖(`references/`, `assets/` 등)에 둔 실행 파일도 L2로 판정됩니다.
- 배포 완료 메일은 작성자와 관리자(승인자)에게 갑니다.

</details>
